# Ronten データモデル設計

## アプリの目的

Ronten は **論点整理力を鍛えるトレーニング記録アプリ** です。
日々の思考や対話を、複数の構造化フレームワークに沿って記録し、
「聞く力 × 構造化する力 × 言語化する力」の3つを継続的に鍛えることを目指します。

## 設計方針: トレーニング種類ごとに独立モデル

Ronten では複数の論点整理トレーニングを扱いますが、
**各トレーニング種類を独立した Django モデルとして実装する** 方針を採用しています。

### この方針を選んだ理由

1. **学習目的との整合性**
   本プロジェクトの第一目的は「Nuxt + Django の業務スタックを身体に入れること」。
   各モデルで CRUD 一周を繰り返すことで、Django の習熟度を上げる。

2. **型の厳密性**
   各トレーニングは構造が違う(3行要約は3フィールド、PREPは4フィールドなど)。
   モデルを分けることで、必須フィールドを DB レベルで強制できる。

3. **段階的実装が可能**
   優先度の高いトレーニングから1つずつ完成させてリリースできる。
   未実装のトレーニングのために、既存モデルを設計し直す必要がない。

### この方針のトレードオフ

- **横断クエリが面倒**: 「全トレーニングを時系列で表示」のような操作には、複数モデルを跨ぐ処理が必要
- **重複コードの可能性**: 各モデルに `created_at`、`updated_at` など共通フィールドが繰り返される

これらの課題が顕在化したら、リファクタリングで以下を検討する:
- 共通フィールドの抽象基底クラス化(`TimeStampedModel`)
- 統一モデル + JSON フィールドへの移行

## モデル一覧と実装状況

| モデル | トレーニング種類 | 頻度 | 実装状況 |
|--------|----------------|------|---------|
| `Summary` | 3行要約 (What/Why/So what) | 毎日 | 🚧 Phase 1 で実装中 |
| `ParaphraseCheck` | 言い換え返しチェック | 毎日 | ⏳ 未着手 |
| `ThreeBoxMemo` | 3箱メモ (事実/感情/要望) | 週3回 | ⏳ 未着手 |
| `PrepMemo` | PREP法 (Point/Reason/Example/Point) | 週3回 | ⏳ 未着手 |
| `SkyRainUmbrella` | 空・雨・傘 (事実/解釈/行動) | 週1回 | ⏳ 未着手 |
| `PyramidMemo` | ピラミッドメモ | 週1回 | ⏳ 未着手 |

## Summary モデル(現状)

最初に実装するトレーニング種類。3つの観点で1件のメモを記録する。

| フィールド | 型 | 説明 |
|----------|---|------|
| `what` | TextField | 何が起きたか、何を見聞きしたか |
| `why` | TextField | なぜそう感じたか、なぜそうなったか |
| `so_what` | TextField | だからどうするか、どう活かすか |
| `created_at` | DateTimeField | 作成日時(自動) |
| `updated_at` | DateTimeField | 更新日時(自動) |

## 将来のリファクタリング候補

現状はモデル別だが、以下の場合は設計の見直しを検討する:

- 全トレーニング横断のストリーク表示などが頻発する場合
  → 共通親モデル `TrainingRecord` の導入
- モデル数が増えて重複コードが目立つ場合
  → 抽象基底クラス `TimeStampedModel` などの導入
- ユーザーが任意のトレーニング種類を作れるようにしたい場合
  → 統一モデル + JSONField への移行

## このドキュメントの更新方針

- 新しいモデルを追加したら、必ず本ドキュメントの「モデル一覧」を更新する
- 設計方針を変更する際は、変更前の判断を残した上で追記する(履歴を消さない)
